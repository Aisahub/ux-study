# 26 条检查清单

每看一个新画面，从头到尾过一遍。**打勾 = 已经查过并且没发现缺陷**，不是"这条原则存在"。

三组的顺序是「缺陷有多难被发现」——A 组站着看就行，B 组必须动手操作，C 组必须先声明读者是谁。

`evidence` 一栏指 `evidence.json` 里 `byPrinciple.<slug>` 的位置。带 **[判断]** 的项目探针量不出来，要靠看截图或读语料。

---

## A 组 · 静止就能看见的（11 条）

### 1. visual-hierarchy 视觉层级（시각적 위계 / Visual hierarchy）
元素拉扯视线的先后顺序，和它们实际的重要程度是否一致。
- evidence: `scale[0..3]` + `desktop-squint.png`
- ❌ 不通过：眯眼图里活下来的东西，不是这个页面存在的理由
- 模板：`这个画面上视线先落在[元素]，但这里最重要的是[元素]。视觉层级和优先级对不上。`

### 2. contrast 对比度（대비 / Contrast）
元素的明度/饱和度离背景和邻居有多远。层级来自对比，不来自颜色本身——同一个颜色在不同环境里会跳出来也会沉下去。**对比是预算**：五个地方都给强对比，等于哪儿都没有。
- evidence: `contrast[]`（按 `textContrast` 升序，第一条就是画面上最弱的控件）
- ❌ 不通过：主要动作的 `textContrast` 不是同屏控件里最高的一档；或正文 < 4.5、大字 < 3.0
- ⚠️ `textContrast: "unmeasurable-image-background"` = 背后是渐变或图片，算不出数字，去看截图
- 模板：`[元素]本该是主要动作，但它和背景的对比并不比周围元素强，所以读起来不像主要动作。拉开明度或饱和度的差距就能解决。`

### 3. scale 尺寸（크기 / Scale）
用大小表示重要性。**通常三档就够，大字不超过两处。**
- evidence: `scale[]`（降序），`cognitive-load.distinctFontSizes`
- ❌ 不通过：`scale[0]` 是没人据此行动的信息（时间戳、ID、版本号）；或大字超过两处；或字号档数 > 5
- 模板：`[元素]是这个画面上最大的东西，但它不是最重要的。尺寸正在告诉用户和我们期望相反的下一步。`

### 4. proximity 邻近性（근접성 / Proximity）
靠得近的读作一伙。**标题到自己内容的间距，要小于到下一组的间距。**
- evidence: `proximity[]` → `readsAsCaptionForFieldAbove: true` 就是命中
- ❌ 不通过：任何一条为 `true`（标签黏在了它不负责的那个输入框上）
- 模板：`[标题]离下面那块和离上面那块一样近，所以它到底在标注哪一块是含糊的。把它和自己的内容之间收紧就能定下来。`

### 5. common-region 公共区域（공통 영역 / Common region）**[判断]**
共享的边框或底色让里面的元素读作一组，在只靠间距不够的时候用。会增加视觉杂乱，所以要省着用。
- evidence: 看 `desktop.png`
- ❌ 不通过：明明是一组的元素没有任何东西把它们圈起来
- 模板：`[这些元素]是一伙的，但没有任何东西把它们归拢。放进同一个带边框的区域里，不用挪动位置就能让关系显形。`

### 6. readability 可读性（가독성 / Readability）
一整块文字能不能舒服地从头读到尾。行距、行长、字距、字号决定它。**逐字都清楚，量一大照样累人。**
- evidence: `readability[]`
- ❌ 不通过：`charsPerLine > 90`、`lineHeightRatio < 1.4`、`longestSentence > 40` 词、或整块无分段
- 模板：`[元素]逐字都认得出，但作为一整块读起来很累——行太长而且排得紧。加大行距就能解决，不用换字体。`

### 7. legibility 易辨性（판독성 / Legibility）
单个字符能不能一眼分辨。笔画粗细、字形、字号、和背景的对比决定它。
- evidence: `readability[].fontSize` / `.contrast`、`contrast[].fontSize`
- ❌ 不通过：正文 < 14px；或对比 < 4.5 的小字
- 模板：`[元素]里的字符在这个字号、这个背景下很难分辨。这是判读性问题不是审美问题——提高对比度或笔画粗细就能解决。`

### 8. cognitive-load 认知负荷（인지 부하 / Cognitive load）
画面在能被行动之前索取的心力。多一个选项、多一个没解释的术语、多一件要记住的事，负荷就多一分。
- evidence: `cognitive-load`
- ❌ 不通过：一屏内可交互元素过多、字号档数过多、文字颜色种类过多——都要对着截图确认
- 模板：`[画面]要求读者在行动前一次抓住太多东西。去掉[什么]能降低认知负荷，又不会拿走他们真正需要的东西。`

### 9. consistency 一致性（일관성 / Consistency）
同一件事在产品里到处都用同一种方式做。两个做同一件事的地方，名字、位置、样式都该一样。
- evidence: `consistency.synonymCandidates` / `.sameTargetDifferentLabel` / `.sameLabelDifferentStyle`
- ⚠️ `synonymCandidates` **会误报**（"确认订单"和"保存设置"同属一个动词族但不是同一件事）。报出去之前先确认这两个真是一件事。
- ❌ 不通过：确认存在同一件事的两种叫法/两种样式
- 模板：`[元素 A]和[元素 B]做的是同一件事，但名字或样式不同。得统一成一个，和产品其余部分吻合的是[哪一个]。`

### 10. signifier 可操作提示（시니파이어 / Signifier）
告诉用户这个元素能被操作的视觉线索——下划线、边框、阴影、圆角矩形。**一个元素可以是可点的却一个提示都不带，那用户就找不到它。** 判断依据是它静止时的样子，在任何 hover 或点击之前。
- evidence: `signifier[]`（按 `visualCueCount` 升序）
- ❌ 不通过：`visualCueCount === 0`；或只有 `cursorPointer` 没有任何视觉线索
- 模板：`[元素]可以点，但不带任何可操作提示——没有任何东西说明它能被操作。加上[下划线／边框]就能让它被找到，布局不用动。`

### 11. disabled-state 禁用态（비활성 상태 / Disabled state）
存在但此刻不能用的元素。**必须看起来不可用**，可能的话还要说明什么条件下会变可用。看起来能用却毫无反应，读起来就是产品坏了。
- evidence: `disabled-state[]`
- ❌ 不通过：`opacity ≥ 0.9` 且 `contrast` 和启用态相当（禁用了却不显禁用）；或 `hasHint: false`
- 模板：`[元素]是禁用状态却看不出禁用，用户会点下去然后判定产品坏了。调暗它并说明什么条件能点亮，两个问题一起解决。`

## B 组 · 必须动手操作才看得见的（10 条）

这一组必须跑 `--act`。静止的截图对它们**什么都证明不了**。

### 12. system-status 系统状态可见性（시스템 상태 가시성 / Visibility of system status）
界面在事情发生的当下就说出正在发生什么。每个动作都有回应，每次等待都有正在进行的迹象，每次状态变化都是被宣告的而不是被发现的。
- evidence: `interactions[].acknowledgedWithin300ms` / `.liveRegions`
- ❌ 不通过：`acknowledgedWithin300ms: false` 且 `newTextAfterSettle` 为空——点了，什么都没发生
- ⚠️ 还要查**过期状态**：改了输入之后，上一次的结果字符串是否还挂在屏幕上
- 模板：`[动作]之后画面[多久]内没有任何变化，用户无从判断成没成。运行期间显示[什么]会让这段等待可读，而不是让他们猜。`

### 13. appropriate-feedback 合适的反馈（알맞은 피드백 / Appropriate feedback）
反馈的大小要配得上它回应的那个动作。小而即时的动作给小回应；长动作要有东西持续说明还在跑。**太响会打断，太轻找不到。**
- evidence: `interactions[].elapsedMs` + `.acknowledgedWithin300ms`
- ❌ 不通过：等待 > 1s 却没有进行中的迹象；或瞬间完成的小动作弹了模态框
- 模板：`[动作]要花[多久]，但回应只有[什么]，大小不匹配——用户被留在[被打断／不确定]的状态。让反馈配上动作的长度就能解决。`

### 14. error-recovery 错误恢复（오류 복구 / Error recovery）
错误消息的第二项任务：指出哪里错了之后，还要说该怎么办。**只报告问题的消息把用户原地留在卡住的地方，只是现在多了一道红框。**
- evidence: `interactions[].liveRegions`、`.newTextAfterSettle`
- ❌ 不通过：消息只有代码/状态（`(code 422)`）、没点名是哪个字段、没说下一步做什么
- 模板：`[消息]说了哪里不对，却没说接下来该做什么，用户只能猜[什么]。把修法写进消息本身，他们不用离开这一页就能继续走。`

### 15. inline-validation 就地校验（인라인 검증 / Inline validation）
在用户还能对答案采取行动的地方校验——挨着字段、他们人还在那个字段里的时候——而不是提交之后把所有问题收进页顶的一张清单。
- evidence: `interactions[].invalidFields` + 下一步是否仍然推进了
- ❌ 不通过：`invalidFields` 非空但下一步照样前进了（**错误拦不住任何东西**）；或只在提交后于页顶报错
- 模板：`[字段]只在提交后才报出它的问题，而且报在页面顶部，用户还得去找它指的是哪个字段。就地校验会把答案放在动作发生的地方。`

### 16. premature-error 过早报错（조급한 오류 / Premature error）
在用户还没把话说完之前就抛出的错误——字段还在被输入就被标红。**这不是提前帮忙，这是在告诉一个正做到一半的人他失败了。**
- evidence: 用 `{"do":"type"}` 输入半截值，看当步的 `invalidFields`
- ❌ 不通过：还在输入中就已经 `aria-invalid=true` / 显示错误
- 模板：`[字段]在用户还在往里打字的时候就变红了，等于把一个没写完的输入判成错误。等到他们离开这个字段再查，校验保留了，指责去掉了。`

### 17. control-fit 控件适配（컨트롤 적합성 / Control fit）
把输入控件配给它要收集的那个选择。下拉框把选项藏在一次点击后面、让它们无法互相比较——收五十个国家是划算的，收三种配送速度是亏本的。
- evidence: `control-fit[]` → `hidesFewOptions: true`
- ❌ 不通过：`optionCount ≤ 4` 却用了下拉（该用单选）
- 模板：`[控件]把用户需要互相比较的[几个]选项藏了起来，把一次选择变成了[几]步。全部摊开就能用看的代替用打开的。`

### 18. smart-defaults 智能默认值（스마트 기본값 / Smart defaults）
表单到手时就已经装着系统自己能算出来的东西——今天的日期、用户所在的国家、上次存的地址。**问一件产品已经知道的事，是让用户替产品干活。**
- evidence: `smart-defaults[]`（`empty: true` + `autocomplete: null`），跨步骤比对是否重复索取同一个值
- ❌ 不通过：字段空着，但产品此前已经拿到过这个值
- 模板：`[字段]是空的，可产品已经知道[什么]了，于是每个用户都要打一遍它本可以自动填上的东西。给它默认值能去掉这一步，又不去掉选择权。`

### 19. emergency-exit 紧急出口（비상구 / Emergency exit）
从一个用户本没打算进入的状态里出来的、明确标示的路，**不需要先做完已经开始的事**。每一步都要有一个，而且必须在这一步里面就看得见，不能靠从外面记住。
- evidence: `emergency-exit.exitControls` / `.dialogs[].hasExit`
- ❌ 不通过：某一步/某个对话框里没有取消或关闭
- 模板：`一旦进了[步骤]，出去的唯一办法就是[做完它／浏览器的后退键]，误入的用户被困住了。放一个看得见的取消，他们就能从进来的路出去。`

### 20. undo 撤销（실행 취소 / Undo）
让动作在发生之后还能被收回。**它真正的价值在点击之前，不在之后**：知道能撤销的用户会去试，不知道的会停下来问人。
- evidence: `emergency-exit.undoMentions`；用 `{"do":"click"}` 走「后退」再看输入还在不在
- ❌ 不通过：后退/取消**清空了已输入的内容**；或破坏性动作只有确认框、没有撤销
- 模板：`[动作]无法收回，所以只能用[一个确认对话框／什么都没有]来把守。让它可撤销，人们就能在不确定的时候放手一试。`

### 21. sense-of-place 位置感（현재 위치 감각 / Sense of place）
不用滚动、不用猜就能回答：我在哪，我怎么来的。**一个从不说明这是第几步、总共几步的流程，让用户没法判断值不值得做完。**
- evidence: `sense-of-place`（`stepIndicator`、`breadcrumb`、`h1`、`title`）
- ❌ 不通过：多步流程里 `stepIndicator: null`；或 `h1` 为空；或 `title` 和画面对不上
- 模板：`[步骤]从不说明它是第几步、共几步，用户没法判断自己是快完了还是刚开始。把位置说出来，他们才能决定要不要继续。`

## C 组 · 必须先声明读者是谁才看得见的（5 条）

**前置条件（来自 testing-with-real-users 课）**：先用一句话写下读者是谁 ——
`读者 = ______（他们的工作／他们已经知道什么／他们为什么打开这一页）`

没有这句话，这 5 条**一条都不能判**。术语算不算术语是关于它的读者的事实，不是关于这个词的事实；不能拿你自己的耳朵当标准。

### 22. plain-language 平实用语（쉬운 말 / Plain language）**[判断]**
用读者已经在用的词，替换团队已经在用的词。**平实不等于简化**——意思整个保留，只是词汇朝读这个人的方向挪。
- evidence: `corpus.buttons` / `.fieldLabels` / `.headings`
- ❌ 不通过：出现只在团队内部有意义的词（数据库字段名、只有供应商这么叫的名字）
- 模板：`[标签]用的是我们内部互相说的词，不是[读者]会用来指同一件事的词。改叫[平实的词]对我们零成本，却去掉了他们行动前必须解码的一个词。`

### 23. paired-term 术语并列（용어 병기 / Paired term）**[判断]**
读者以后在别处还会再遇到的技术词要保留，但要把平实的词写在旁边：多数读者不认识这个术语时平实词在前，多数认识时技术词在前。
- evidence: `corpus`
- ❌ 不通过：术语必须保留（别处会再遇到）却孤零零出现；或顺序反了（读者不认识的术语摆在前面）
- 模板：`[术语]必须留着，因为[他们再遇到它的地方]用的就是这个词。写成"[平实词]（[术语]）"能让它继续可用，又不至于把"认识它"变成看懂这句话的门票。`

### 24. expanded-acronym 缩写展开（약어 풀어쓰기 / Expanded acronym）
缩写要在读者遇到它的地方写全，**并且在半路进来的读者会遇到它的地方再写一次**。人不是从顶上开始读的，所以只在顶部展开一次，等于多数读者永远看不到。
- evidence: `expanded-acronym[]` → `expandedNearby: false`
- ❌ 不通过：任何一条 `expandedNearby: false`
- 模板：`[缩写]出现在这里，周围没有任何东西展开它，从中途进入这一页的读者无从知道它代表什么。在这个位置写上"[完整词组]（[缩写]）"只花一行。`

### 25. mental-model 心智模型（멘탈 모델 / Mental model）**[判断]**
用户相信这东西是怎么运作的——不是它实际做什么，也不是文档怎么写。**它决定用户预期一个控件会做什么，而界面必须对它负责，不管它准不准确。**
- evidence: `corpus.buttons`（动词）+ `interactions[].newTextAfterSettle`（实际结果）
- ❌ 不通过：控件按系统看自己的方式命名；或结果和读者会预测的不一样（"预约"其实只是提交申请）
- 模板：`[控件]的行为遵循的是系统对自己的理解，不是[读者]会预期的样子。他们会预测[什么]，所以让行为迎合预期，比用一个 tooltip 解释掉它更安全。`

### 26. model-inertia 模型惯性（모델 관성 / Mental-model inertia）**[判断]**
用户已经握着的模型有多不情愿让位。**遇到和自己所信相矛盾的东西时，用户更常得出的结论是界面坏了，而不是自己的信念错了。**
- evidence: `corpus.bodyText`
- ❌ 不通过：画面要求用户放弃一个他们已经持有的信念，却没有任何过渡
- 模板：`[变化]要求用户放弃他们关于[什么]已经相信的东西。那个信念不容易挪动，所以预计这会被读成[画面]的毛病，而不是一件值得学的新东西。`

## 质量闸：报出去之前，每条发现自查

这两条来自 heuristic-evaluation 和 testing-with-real-users 课，**不按画面打勾**，而是每条发现都要过。

### 格式纪律 — named-heuristic 具名启发式（명명된 휴리스틱 / Named heuristic）
判断必须锚定在一条具名原则上，而不是评审者自己的口味。**名字才是让第三个人能去核对这条发现、而不是只能选择相信你的东西。**

一条发现必须同时有：
1. **元素** — 用画面自己的叫法（用户看到的那个字，不是 CSS 类名）
2. **原则** — 上面 26 条里的一个 slug
3. **观察** — 出了什么问题，写成第三个人能自己去复现的样子
4. **修法** — 具体到能动手

### 四分法 — 报之前给每条发现贴一个标签
（来自 `content/specimen-report.md`，学员就是拿这四类练评审的）

- **sound 成立** — 发现是对的，是对着它点名的那条原则论证的，写成了别人能据此行动的话 → **报**
- **wrong-principle 挂错原则** — 元素对、观察对，但选的原则不是这个元素破坏的那一条 → **换成对的原则再报**
- **taste 口味** — 一个偏好套着原则的名字。**没说清对读者来说出了什么问题，所以没人能据此行动** → **丢掉**
- **not-a-defect 不是缺陷** — 把一个寻常安排读成了毛病，照它的修法改反而会引入它声称发现的那个缺陷 → **丢掉**

判 taste 最快的一问：**"这里对读者具体出了什么问题？"** 答不上来，或者答案只是"我见过的都不是这样"，就是 taste。

> 反例（taste）：*"搜索框在左边，我用过的管理后台都放右边，所以感觉反了。"* —— 没有任何读者因此受损，只是不合习惯。
> 反例（not-a-defect）：*"保存按钮在表单最底下，手机上要划到底。应该固定在屏幕底部。"* —— 表单末尾放保存是常规做法；固定浮层反而会遮住最后一个字段。

### 独立性 — independent-evaluation 独立评估（독립 평가 / Independent evaluation）
多人评审时各自走完并各自写完再交换。**两个人分头得出同一条发现是证据；一个人先开口之后两个人达成一致不是。**
